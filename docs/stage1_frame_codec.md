# 阶段 1：FrameCodec 协议编解码

## 1.阶段目标
本阶段实现 TinyKVCache 的应用层协议编解码模块。

协议格式定义如下：
```text
4 字节 payload 长度 + payload 内容
```
其中长度字段使用网络字节序，也就是大端序。

## 2.为什么需要应用层协议
TCP 是**字节流协议**，不保留应用层消息边界。因此，在 TCP 连接中，一次 send 的数据，接收端可能：

1. 一次 recv 收到完整一条消息；
2. 多次 recv 才收到完整一条消息；
3. 一次 recv 收到多条消息；
4. 一次 recv 收到一半消息；

因此，不能把一次 recv 当做一条命令。

## 3.协议格式
每条消息由两部分内容组成：
```
header: 4 字节，无符号整数，表示 payload 长度，采用网络字节序
body：  N 字节，表示 payload 内容
```

例如，PING 编码后是：
```
00 00 00 04 50 49 4E 47
```

## 4.encode 流程

1. 检查 payload 是否超过最大长度；
2. 使用 htonl 把长度传换成网络字节序；
3. 创建 4 + payload.size() 大小的字符串；
4. 前 4 字节写入长度；
5. 后面写入 payload；

## 5.decode 流程

1. 把新收到的数据追加到连接级 buffer；
2. 如果 buffer 不足 4 个字节，说明连长度头都没接受完整，等待下一数据；
3. 读取前 4 字节长度字段；
4. 使用 ntohl 转换成主机字节序；
5. 如果超过最大长度限制，则抛异常；
6. 如果 buffer 不足 4 + payloadLen，说明发生半包，等待下一次数据；
7. 如果 buffer 足够，取出 payload；
8. 删除已经消费的 frame；
9. 继续尝试解析下一条消息。

## 6.为什么 buffer 必须是连接级别的？
因为**每个 TCP 连接都有独立的数据流**，不同客户端的半包状态不能混在一起。

因此，后续要编写的服务端中，每个连接都需要维护自己的 read_buffer。

## 7.最大 frame 限制
FrameCodec 限制单条 payload 最大为 1 MiB。

原因是：如果不限制长度，异常客户端可以发送一个非常大的长度字段，例如 2GB，导致服务端一直等待巨大 body，造成内存压力。

## 8.本阶段测试覆盖
本阶段测试覆盖：
1. 单条完整消息
2. 粘包
3. 半包
4. 每次只收到一个字节
5. 两条完整消息加一条半包；

## 9.面试表达
TCP 是字节流协议，不保留应用层消息边界，所以会出现粘包和半包。

我在项目中设计了一个简单的长度字段协议：每条消息前 4 字节表示 payload 长度，后面跟 payload 内容。

服务端会为每个连接维护 read_buffer，每次 recv 后把数据追加进去，然后循环判断 buffer 中是否已经有完整 frame。

如果不足 4 字节，说明长度头没收完整；如果不足 4 + payload_len，说明 body 没收完整；只有完整后才取出 payload 并删除已消费数据。

这样可以同时处理半包、粘包和一次收到多条消息的情况。

## 10.自测问题

### （1）为什么 TCP 会出现粘包？
因为 TCP 是字节流协议，不保存应用层的消息边界。因此，可能出现连续 send() 两条消息，接收端一次 recv() 收到两条消息的数据。

### （2）为什么 TCP 会出现半包？
因此一次 recv 不能保证读取到完整的业务消息，如果消息过大或者发生网络切片，接收端可能多次 recv 才能拿到完整消息。

### （3）为什么不能用换行符作为协议边界？
可以用，但不适合所有场景。如果 payload 本身可能包含换行符，就需要转义或额外处理。长度字段协议更通用，可以支持任意二进制内容。

### （4）为什么长度字段是 4 字节？
4 字节 uint32_t 最大可以表示约 4GB 的长度，本项目虽然限制位 1MiB，但使用 4 字节长度字段是常见设计，简单、够用、容易解析。

### （5）为什么使用`htonl`和`ntohl`？
因为不同机器的 CPU 字节序可能不同。为了保证网络传输的协议字段一致，发送前使用`htonl`转换成网络字节序，接收后使用`ntohl`转回主机字节序。

### （6）为什么 `decode()` 要接收 `std::string& buffer`？
因为半包数据需要夸多次 recv 保存，如果 buffer 是局部变量，那么函数结束后半包数据就丢失了。所以，后续每个连接都要有自己的 read_buffer。

### （7）为什么 decode 里要用 while 循环？
因为一次 recv 可能包含多条完整的消息，所以使用 while 循环保证在一次调用中尽可能解析出所有完整的 frame。
